# v0.1d review disposition

This note records how the independent registry, rendering, documentation, and evaluation findings were resolved before delivery.

## Accepted and implemented

- **Canonical exit codes:** accepted-exit validation now rejects JavaScript negative zero and performs semantic duplicate detection in addition to the strict TypeBox schema. The same validator is used for registry definitions and serialized detail snapshots, preventing `[-0, 0]` from passing registry validation and later failing after JSON converts both values to zero.
- **Regression coverage:** YAML and JSON definitions cover `[-0]` and `[-0, 0]`; an attributable negative-zero user override quarantines the bundled definition; malformed serialized snapshots are rejected; and valid accepted nonzero details still round-trip through JSON.
- **Final Pi rendering state:** collapsed rendering uses the final Pi `context.isError` state for success/error color. When another middleware marks a policy-accepted nonzero exit as erroneous, the summary now says `accepted policy; marked error` instead of presenting contradictory success output.
- **Network scope:** README, lifecycle, canonical design, and evaluation language now distinguish network-free controlled CLI execution from npm dependency installation, audit, and packed production installation, which may contact the npm registry.

## Intentionally retained or rejected

- **Reject rather than normalize negative zero:** registry data is trusted declarative configuration, so a non-canonical representation fails closed with normal provenance and quarantine behavior. Silent normalization would hide a duplicate such as `[-0, 0]` and weaken the strict-definition contract.
- **Current package smoke installation:** the smoke test continues to perform a fresh production install of the packed tarball. This validates runtime dependency placement and may resolve `yaml` through npm. Offline package installation is not claimed; the deterministic CLI execution itself remains fixture-based and makes no GitHub or third-party CLI network requests.
- **No broader rendering or middleware redesign:** the adapter still omits an `isError` patch for policy-accepted results so earlier middleware decisions survive. The renderer consumes Pi's final state without changing middleware ordering or result classification.

## Scope decision

No ADR is needed because the fixes enforce the already documented strict, serializable accepted-exit contract and align rendering with Pi's existing middleware result. No version/help/man execution, documentation retrieval, stdin, rich per-CLI schema, lazy activation, arbitrary environment/cwd control, or Windows support was added.
